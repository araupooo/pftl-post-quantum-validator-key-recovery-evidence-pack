36: /*
37:     Validator key manifests
38:     -----------------------
39: 
40:     Suppose the secret keys installed on a Ripple validator are compromised. Not
41:     only do you have to generate and install new key pairs on each validator,
42:     EVERY rippled needs to have its config updated with the new public keys, and
43:     is vulnerable to forged validation signatures until this is done.  The
44:     solution is a new layer of indirection: A master secret key under
45:     restrictive access control is used to sign a "manifest": essentially, a
46:     certificate including the master public key, an ephemeral public key for
47:     verifying validations (which will be signed by its secret counterpart), a
48:     sequence number, and a digital signature.
49: 
50:     The manifest has two serialized forms: one which includes the digital
51:     signature and one which doesn't.  There is an obvious causal dependency
52:     relationship between the (latter) form with no signature, the signature
53:     of that form, and the (former) form which includes that signature.  In
54:     other words, a message can't contain a signature of itself.  The code
55:     below stores a serialized manifest which includes the signature, and
56:     dynamically generates the signatureless form when it needs to verify
57:     the signature.
58: 
59:     An instance of ManifestCache stores, for each trusted validator, (a) its
60:     master public key, and (b) the most senior of all valid manifests it has
61:     seen for that validator, if any.  On startup, the [validator_token] config
62:     entry (which contains the manifest for this validator) is decoded and
63:     added to the manifest cache.  Other manifests are added as "gossip"
64:     received from rippled peers.
65: 
66:     When an ephemeral key is compromised, a new signing key pair is created,
67:     along with a new manifest vouching for it (with a higher sequence number),
68:     signed by the master key.  When a rippled peer receives the new manifest,
69:     it verifies it with the master key and (assuming it's valid) discards the
70:     old ephemeral key and stores the new one.  If the master key itself gets
71:     compromised, a manifest with sequence number 0xFFFFFFFF will supersede a
72:     prior manifest and discard any existing ephemeral key without storing a
73:     new one.  These revocation manifests are loaded from the
74:     [validator_key_revocation] config entry as well as received as gossip from
75:     peers.  Since no further manifests for this master key will be accepted
76:     (since no higher sequence number is possible), and no signing key is on
77:     record, no validations will be accepted from the compromised validator.
78: */
