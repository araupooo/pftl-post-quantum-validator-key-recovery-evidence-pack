| F-01 | HIGH | MEASURED | Master-key loss is unrecoverable by design | Drill C: without the master secret no new manifest can be signed, so rotation is impossible; the only path is a new validator identity. Pinned code: ValidatorKeys.cpp loads the master key only from [validator_token]/[validation_seed]; no recovery path exists. Docs: losing validator-keys.json means 'you will need to create a completely new validator identity' (ValidatorKeyUpdate.md). | Adopt the 3-of-5 Shamir backup in docs/backup-spec.md for every master secret before mainnet; pre-generate a revocation manifest and store it with the shares. |
| F-02 | HIGH | MEASURED | No post-quantum signature support in the pinned code | grep over src/, include/, docs/ of postfiatd 0085a1ff for ml-dsa/mldsa/slh-dsa/slhdsa/dilithium/post-quantum/sphincs returns zero matches. KeyType has exactly two values (secp256k1, ed25519). The whitepaper section 1.11 promises 'Accounts and validators sign with ML-DSA-65 from genesis' — the promise is unimplemented in the shipped testnet code. | Treat the ML-DSA-65 validator layer as a design requirement, not a shipped property; plan the migration in docs/pq-migration.md before any mainnet claim. |
| F-03 | HIGH | SPECIFIED | validator-keys.json is deleted on container restart | ValidatorKeyUpdate.md and NodeSetup.md: the file holding the master validator keys lives inside the Docker container at /root/.ripple/validator-keys.json and 'is deleted when the Docker container is restarted or recreated'. The documented mitigation is a manual docker cp before every restart; nothing enforces it. | Automate the pre-restart backup (hook the compose restart path) and verify the backup by restoring it in a lab on a schedule; see docs/runbook.md. |
| F-04 | HIGH | MEASURED | Post-quantum signatures cannot fit the 512-byte manifest cap | Manifests are capped at 512 bytes (docs/MANIFEST_FLOOD_HOTFIX.md). ML-DSA-65 signatures are 3,309 bytes (FIPS 204 Table 2) — 6.5x the cap; the smallest SLH-DSA signature is 7,856 bytes (FIPS 205 Table 2) — 15.3x the cap. Live manifests are 225-246 bytes. Any PQ migration requires a manifest-format change, not a drop-in key swap. | Design the PQ manifest format (larger cap or external signature references) as part of the migration; do not assume the current format survives. |
| F-05 | MEDIUM | MEASURED | Passphrase-derived seeds are brute-forceable | Seed.cpp generateSeed(): the seed is the first 16 bytes of SHA-512/2 of the passphrase, with no salt and no stretching. Any [validation_seed] or account seed created from a human passphrase inherits the passphrase's entropy. randomSeed() (CSPRNG, 16 bytes) is the safe path. | Never create validator seeds from passphrases; use randomSeed()/validation_create with no secret argument; audit existing deployments for passphrase seeds. |
| F-06 | MEDIUM | MEASURED | [validation_seed] mode collapses the identity to one key | ValidatorKeys.cpp: in seed mode the secret key is generateSecretKey(secp256k1, seed), master = signing = the derived key, sequence 0. There is no manifest, no rotation, and no revocation: losing or compromising that one key ends the identity. | Use [validator_token] (manifest) mode for every validator; treat seed mode as a bootstrap-only path. |
| F-07 | MEDIUM | MEASURED | No Shamir/threshold backup exists in the pinned code or docs | grep for shamir/threshold/share in the pinned repo and docs returns no backup procedure; the documented backup is a single-file copy (docker cp) to 'a secure location'. A single copy is a single point of failure and a single point of theft. | Adopt the 3-of-5 Shamir backup specified in docs/backup-spec.md (reference implementation in scripts/shamir.py, verified by drill D). |
| F-08 | MEDIUM | SPECIFIED | Revocation depends on the master key surviving | Manifest.cpp: a revocation is a manifest with sequence 0xFFFFFFFF, authenticated by the master key. If the master key is lost (not merely compromised), no revocation can be published; the key can only be removed from trust by the VL publisher. No pre-generated revocation manifest is documented anywhere in the pinned repo. | Pre-generate a revocation manifest at key-creation time and store it with the Shamir shares (it is useless without the master signature, so it is safe to escrow). |
